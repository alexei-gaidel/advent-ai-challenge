# 18 — MCP-инструмент с периодическим выполнением

**Задание:** сделать MCP-инструмент с отложенным или периодическим выполнением, который
сохраняет данные, выполняется по расписанию и возвращает агрегированный результат.
Итог — агент, который работает 24/7 и периодически выдаёт сводку.

Задача: раз в восемь часов собирать курсы криптовалют (BTC, ETH, LTC, XMR, ETC) и отправлять сводку в Telegram.

## Запуск

```bash
cd 18-scheduled-mcp
python3 market.py --once           # снять наблюдение с биржи
python3 scheduler.py --setup       # завести задания
python3 scheduler.py               # планировщик 24/7, Ctrl+C для выхода
python3 scheduler.py --once        # один проход — его же вызывает GitHub Actions
python3 schedule_demo.py           # ускоренный прогон: минута вместо суток
python3 market_server.py --selftest # инструменты MCP без клиента
python3 web.py                     # панель на http://localhost:8018
```

Зависимостей нет. Telegram настраивается двумя строками в корневом `.env`
(`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`); без них сводка пишется в
`data/outbox.log`, и всё остальное работает.

## Архитектура

```
   ┌── по расписанию ──┐
   ↓                   │
market.py  →  store.py  →  digest.py  →  notify.py → Telegram
(CoinGecko)  JSONL+SQLite   агрегация     доставка
                   ↑
            market_server.py (MCP)  →  агент отвечает цифрами
```

Разделение нарочное: **сбор, хранение, агрегация и доставка ничего не знают про MCP**,
а MCP-сервер ничего не знает про расписание — он просто читает то, что уже накоплено.
Поэтому сводка одинаково уходит и в чат по расписанию, и агенту по запросу.

## Два хранилища, и это не избыточность

| Что | Где | Почему так |
|---|---|---|
| Ряд наблюдений | `data/samples.jsonl` — **коммитится в репозиторий** | в GitHub Actions между запусками ничего не сохраняется; файл в репозитории — единственный способ копить историю без сервера |
| Задания и журнал запусков | `schedule.db` (SQLite), локально | нужны живому планировщику; в Actions бессмысленны, потому что процесс живёт секунды |

Задание разрешает «JSON или SQLite» — здесь пригодилось и то, и другое, каждое
по своей причине. Пути обоих хранилищ переопределяются переменными
`ADVENT_SAMPLES` и `ADVENT_SCHEDULE_DB`.

## Расписание

Три вида заданий — задание просило «отложенное **или** периодическое», сделаны оба:

| Вид | Периодичность | Что делает |
|---|---|---|
| `collect` | раз в час | снимает наблюдение с биржи и дописывает в ряд |
| `digest` | раз в 8 часов | собирает сводку и отправляет в Telegram |
| `remind` | одноразовое | срабатывает один раз в заданное время и выключается |

Журнал запусков (`runs`) — это доказательство, а не обещание: по нему видно, что
расписание действительно соблюдалось.

```
13:53:40  collect       error CoinGecko: превышен лимит запросов, нужно реже
13:53:40  digest        ok    инструментов в сводке: 0 · сводка записана в outbox.log
13:53:49  remind-demo   ok    напоминание отправлено
13:54:00  collect       ok    наблюдений: 5
13:54:10  digest        ok    инструментов в сводке: 5 · сводка записана в outbox.log
13:54:20  collect       ok    наблюдений: 5

всего 6, с ошибкой 1
одноразовое напоминание после срабатывания: выключено
```

Это вывод `schedule_demo.py`: интервалы там 20 и 30 секунд вместо часа и восьми часов.
Первая строка с ошибкой — не постановка: сбор действительно упёрся в лимит CoinGecko,
и видно главное — упавшее задание не остановило ни планировщик, ни остальные задания.
Логика планировщика настоящая — ровно та, что уезжает в Actions; ускорено только время,
иначе демонстрация заняла бы сутки.

## Агрегированный результат

```
Курсы · 2026-09-23 13:54 UTC

BTC      85 672 USD   -0.45% за сутки
ETH       2 714 USD   -1.48% за сутки
LTC       62.53 USD   +1.63% за сутки
XMR      563.12 USD   -2.02% за сутки
ETC        9.41 USD   +3.92% за сутки
```

Сводка намеренно короткая: цена и изменение за сутки, больше ничего. Коридоры цен
и счётчики наблюдений из сообщения убраны — для разбора есть `market_history`,
а в сводке, которая приходит в чат три раза в день, они только мешают.

## Инструменты MCP

| Инструмент | Аргументы | Что делает |
|---|---|---|
| `market_digest` | `period` (enum: 8h, 24h, 7d) | сводка: цена и изменение за сутки |
| `market_history` | `symbol`*, `limit` | ряд наблюдений по монете: время, цена, изменение |
| `collect_now` | — | снять наблюдение немедленно, не дожидаясь расписания |
| `list_jobs` | — | задания и время следующего запуска |
| `list_runs` | `limit` | журнал запусков: соблюдалось ли расписание |
| `schedule_reminder` | `text`*, `after_minutes`* | отложенное напоминание: один раз и выключится |

`*` — обязательный аргумент. Агент из задания 17 подключается к серверу без правок:
менялась только команда запуска.

```
вы → Что с рынком за сутки? Назови, что выросло, а что упало.
  🔧 market_digest({'period': '24h'})
агент ← - Выросли: ETC 9.41 (+3.92%), LTC 62.53 (+1.63%)
        - Упали: XMR 563.12 (-2.02%), ETH 2 714 (-1.48%), BTC 85 672 (-0.45%)
```

Цифры в ответе — из накопленного ряда, а не из головы модели.

## Где это крутится 24/7

Выбран **GitHub Actions** — `.github/workflows/market-digest.yml` в корне репозитория:
`cron: "0 */8 * * *"` плюс ручной запуск. Workflow вызывает тот же
`scheduler.py --once --force`, что работает локально, и коммитит обновлённый
`samples.jsonl` обратно. Токен и chat_id лежат в секретах репозитория, в коде их нет.

Честные ограничения этого варианта:

- cron в Actions **не точен**: запуск может опоздать на 5–20 минут;
- на публичных репозиториях расписание **отключается после 60 дней** без активности
  (нас спасает то, что workflow сам коммитит данные);
- состояние живёт только в репозитории, потому ряд и коммитится.

Сравнение трёх вариантов, если задача изменится:

| Вариант | Цена | Когда подходит |
|---|---|---|
| launchd на Маке | 0 | ноутбук включён большую часть дня, пропуски не критичны |
| **GitHub Actions** | 0 | исходящий дайджест по расписанию — выбран |
| VPS | 3–5 $/мес | нужен **входящий** поток: бот отвечает на вопросы, веб-панель доступна извне, история без пропусков |

Ключевая развилка — «получать» или «отвечать». Для исходящей сводки сервер избыточен;
он окупается, когда захочется задать боту вопрос и получить ответ из MCP.

Для переезда на сервер достаточно юнита:

```ini
# /etc/systemd/system/advent-market.service
[Unit]
Description=Advent market scheduler
After=network-online.target

[Service]
Type=simple
WorkingDirectory=/opt/advent/18-scheduled-mcp
EnvironmentFile=/opt/advent/.env
ExecStart=/usr/bin/python3 scheduler.py
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

## Грабли

| Симптом | Причина |
|---|---|
| Курс XMR показывал 118 вместо 563 | Binance **делистил Monero**, но пара `XMRUSDT` осталась в API и молча отдавала застывшую цену: последняя сделка была за две недели до запроса. Ошибку видно только глазами — формат ответа корректен, поля заполнены. Перешли на CoinGecko и добавили проверку свежести: источник возвращает `last_updated_at`, и наблюдение старше трёх часов помечается как устаревшее |
| Половина проходов падает с 429 | CoinGecko на бесплатном тарифе пускает несколько запросов в минуту. Для расписания раз в час это неважно, но демонстрация с интервалом в 8 секунд упиралась в лимит — интервалы пришлось поднять |
| Агент отвечает не теми цифрами, что в сводке | MCP-сервер поднимается **отдельным процессом** и читает пути по умолчанию: подмены путей в памяти он не видит. Лечится переменными окружения `ADVENT_SAMPLES` и `ADVENT_SCHEDULE_DB` |
| В Actions ничего не собирается | на чистой машине нет `schedule.db`, задания не заведены и «время не подошло». Поэтому workflow вызывает `--once --force` |
| Одноразовое задание срабатывает снова | после запуска его нужно не переносить вперёд, а деактивировать: `every = 0` означает «выключить после выполнения» |
| Падение одного задания останавливает всё | каждое задание выполняется в своём `try`, ошибка пишется в журнал со статусом `error`, остальные продолжают |

## Выводы

- **«24/7» проверяется журналом, а не обещанием.** Таблица `runs` с временем и статусом
  каждого запуска — единственный способ отличить работающее расписание от написанного.
- **Ускорение времени — не жульничество, а способ тестировать.** Логика планировщика
  одна и та же; поменялись только интервалы, и минута заменила сутки.
- **Место хранения диктуется местом запуска.** Выбор Actions сразу определил формат
  данных: SQLite между запусками не выживет, а JSONL в репозитории — да.
- **Разделение слоёв окупилось сразу.** Сводку считает одна функция, а потребителей
  у неё трое: Telegram, MCP-инструмент и веб-панель. Ни один не знает про остальных.
- **Молчаливо неверные данные опаснее ошибки.** Застывшая пара на бирже отдавала
  валидный JSON с правильными полями — и только человек, знающий реальную цену Monero,
  заметил подвох. Поэтому источник теперь обязан сообщать время последнего обновления,
  а наблюдение — помечаться устаревшим.
