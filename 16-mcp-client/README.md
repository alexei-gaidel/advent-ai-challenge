# 16 — Подключение к MCP

**Задание:** установить MCP-клиент, установить соединение и получить список доступных
инструментов. Проверить, что соединение устанавливается и список возвращается корректно.

## Запуск

```bash
cd 16-mcp-client
python3 mcp_demo.py                        # три публичных сервера + свой локальный
python3 mcp_demo.py https://любой/mcp      # произвольный сервер
python3 web.py                             # обозреватель на http://localhost:8016
python3 mcp_server.py --selftest           # прогон своего сервера без клиента
```

Зависимостей нет: клиент и сервер написаны на стандартной библиотеке.

## Почему свой клиент, а не SDK

Официальный SDK ставится через pip, а в этом репозитории правило — только стандартная
библиотека. Причина не в упрямстве: дни копируются вперёд, и зависимость, добавленная
здесь, поехала бы во все последующие, а запуск перестал бы сводиться к `python3 file.py`.

При этом объём работы сопоставим: клиент — 150 строк, сервер — 120. Зато видно сам
протокол, а в задании 17 нужно показать «регистрацию инструмента и описание входных
параметров» — в SDK это прячется за декоратором и генерируется из аннотаций типов.

## Протокол: три сообщения

MCP — это JSON-RPC 2.0 поверх транспорта. Для «подключиться и получить инструменты»
нужно ровно три сообщения:

```jsonc
// 1. клиент представляется
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{
   "protocolVersion":"2025-06-18","capabilities":{},
   "clientInfo":{"name":"advent-mcp-client","version":"0.1.0"}}}

// ответ сервера
{"jsonrpc":"2.0","id":1,"result":{
   "protocolVersion":"2025-06-18",
   "capabilities":{"tools":{"listChanged":false}},
   "serverInfo":{"name":"advent-demo-server","version":"0.1.0"}}}

// 2. уведомление о готовности — без id, ответа нет
{"jsonrpc":"2.0","method":"notifications/initialized"}

// 3. запрос инструментов
{"jsonrpc":"2.0","id":2,"method":"tools/list"}
```

Транспорта два, и оба реализованы:

| Транспорт | Как устроен | Для чего |
|---|---|---|
| Streamable HTTP | POST с JSON-RPC, ответ обычным JSON или потоком SSE | публичные серверы |
| stdio | дочерний процесс, JSON построчно в stdin/stdout | локальный сервер |

| Свой сервер | stdio | 2025-06-18 | 3 | 0.04 |

Все четыре соединения устанавливаются, списки возвращаются. Ни один публичный сервер
не потребовал авторизации. Разброс по времени показателен: чужой сервер по сети отвечал
до 12 секунд, свой по stdio — за 0.04.

Пример инструмента с чужого сервера, со схемой аргументов:

```
ask_wiki_question
  Ask any question about a GitHub repository

  схема аргументов:
    repoName: string | array · обязательный
      GitHub repository or list of repositories (max 10) in owner/repo format.
    question: string · обязательный
      The question to ask about the repository.
```

Тип `string | array` — это union через `anyOf`, а не привычное `type`. В первой версии
разбор схемы показывал такой аргумент как `?`; пришлось научить клиент разворачивать
`anyOf` и `oneOf`.

## Свой сервер

`mcp_server.py` — минимальный, но настоящий MCP-сервер на stdio: `initialize`,
`tools/list`, `tools/call`, уведомления без ответа. Три инструмента-заготовки —
`ping`, `echo`, `now` — с честными `inputSchema`. В задании 17 на этом каркасе вырастут
инструменты вокруг git.

Регистрация инструмента — это просто запись в списке:

```python
{
    "name": "now",
    "description": "Текущее время сервера в выбранном формате.",
    "inputSchema": {
        "type": "object",
        "properties": {
            "format": {"type": "string", "description": "Формат вывода времени",
                       "enum": ["iso", "date", "time", "unix"], "default": "iso"},
        },
        "required": [],
    },
}
```

## Проверка чужим клиентом

Самое убедительное доказательство совместимости — посмотреть на наш сервер не своими
глазами. Официальный **MCP Inspector** (реализация на TypeScript) подключается к нему
и видит те же три инструмента:

```bash
npx -y @modelcontextprotocol/inspector --cli python3 mcp_server.py --method tools/list
```

```jsonc
{"name":"echo","description":"Возвращает переданный текст без изменений.",
 "inputSchema":{"type":"object","properties":{"text":{"type":"string",
 "description":"Что вернуть обратно"}},"required":["text"]}}
```

И вызов инструмента тоже:

```bash
npx -y @modelcontextprotocol/inspector --cli python3 mcp_server.py \
    --method tools/call --tool-name echo --tool-arg text="проверка совместимости"
```

```json
{"content": [{"type": "text", "text": "проверка совместимости"}], "isError": false}
```

`npx` запускается разово и в репозиторий ничего не добавляет — правило «без
зависимостей» не нарушено.

## Грабли

| Симптом | Причина |
|---|---|
| HTTP 406 в ответ на корректный JSON-RPC | нужен заголовок `Accept: application/json, text/event-stream` — сервер вправе ответить потоком |
| Ответ не парсится как JSON | это SSE: строки `event: message` и `data: {…}`, JSON лежит в `data` |
| Второй запрос отвергается | сервер выдал `Mcp-Session-Id` в заголовках ответа на `initialize`, его надо возвращать во всех последующих запросах |
| Сервер молчит после `initialize` | не отправлено уведомление `notifications/initialized` |
| Тип аргумента показывается как `?` | схема описывает union через `anyOf`, а не `type` |
| Свой stdio-сервер «ломается» без причины | что-то напечатано в stdout: там только JSON-RPC, всё человеческое — в stderr |

## Выводы

- **MCP проще, чем кажется со стороны.** Для списка инструментов хватает трёх сообщений
  JSON-RPC; вся «магия» — в договорённости об именах методов и схеме ответа.
- **Схема инструмента и есть интерфейс.** Именно `inputSchema` объясняет модели, что
  передавать; описания и типы важнее самой функции.
- **Совместимость надо проверять чужой реализацией.** Свой клиент может «договориться»
  со своим сервером о чём угодно — ценность появляется, когда наш сервер открывает
  инспектор, а наш клиент читает DeepWiki.
- **Транспорт не абстракция ради абстракции.** stdio и HTTP различаются заметно: сессии
  и SSE против построчного JSON, 0.04 секунды против 12.
