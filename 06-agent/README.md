# 06 — Первый агент

**Задание:** реализовать простого агента, который принимает запрос пользователя,
отправляет его в LLM через API, получает ответ и выводит результат в интерфейсе.
Важно: агент должен быть отдельной сущностью, а не одним вызовом API, а логика
запроса и ответа — инкапсулирована в агенте.

## Запуск

```bash
cd 06-agent
python3 web.py            # откроется http://localhost:8006
```

Открываются две панели. Каждая — самостоятельный агент со своей памятью, настройками
и счётчиками. Кнопка «+ ещё чат» добавляет панель, «Клонировать» — копию агента с теми
же настройками, верхнее поле спрашивает сразу все панели.

Нужны оба ключа в корневом `.env`: `DEEPSEEK_API_KEY` и `GROQ_API_KEY`.

## Где проходит граница агента

```
браузер ──id агента + текст──► web.py ──agent.ask(text)──► Agent ──► providers ──► LLM
                                 │                          │
                       только транспорт            вся логика запроса-ответа:
                       и отрисовка                 system + память + данные,
                                                   счётчики, история
```

`web.py` не собирает массив `messages`, не знает адресов провайдеров и не разбирает
их ответы — он умеет только попросить агента ответить. Состояние агента живёт **на
сервере**, в экземпляре класса, а не в браузере: страница знает лишь `id`.

Это же делает split-screen честным — две панели это два независимых объекта, а не
две вкладки над одним вызовом API.

| Файл | Что внутри |
|------|------------|
| `agent.py` | класс `Agent` (настройки, память, счётчики, `ask`), реестр агентов, встроенные и пользовательские роли |
| `providers.py` | каталог моделей двух провайдеров, единый `call()`, тарифы |
| `toon.py` | кодер TOON и замер экономии |
| `web.py` | HTTP-сервер и страница |

## Настройки агента

| Настройка | Что делает |
|---|---|
| Модель | пять моделей двух провайдеров: DeepSeek и четыре Groq (7B…120B) |
| Роль | пресет, подставляющий текст в `system_prompt`; поле остаётся редактируемым. Свои роли создаются прямо в интерфейсе |
| `system_prompt` | отдельное поле для постоянных инструкций |
| Температура | ползунок 0–2 (см. задание 04) |
| `max_tokens`, `stop` | потолок длины и стоп-последовательности (см. задание 02) |
| Память | галочка «помнить» и глубина — последние N сообщений |
| Данные | JSON, уходящий в промпт как контекст, в формате JSON или TOON |

Счётчики в шапке панели: вызовов, токенов (отдельно в запрос и в ответ), стоимость по
тарифам, сообщений в памяти. У каждого ответа — своё время, токены и цена.

## Роли

Встроенные роли разделены на две группы. Общие: ассистент, строгий редактор, переводчик,
критик, объясняющий ребёнку, аналитик данных. Для работы с кодом:

| Роль | Чем занимается |
|---|---|
| Программист | пишет рабочий код без лишних зависимостей, потом короткое пояснение |
| Тестировщик | ищет, чем сломать: границы, пустой ввод, юникод, отказ сети; выдаёт тест-кейсы |
| Архитектор | отвечает решениями, а не строками: границы модулей, состояние, узкие места |
| Ревьюер кода | ищет настоящие дефекты, не стилистику: логика, исключения, гонки, утечки |
| Отладчик | по traceback называет вероятную причину и минимальную правку |
| Технический писатель | описание кода: что делает, как запустить, чего не умеет |

Кнопка **+** рядом со списком заводит свою роль: название и описание для
`system_prompt`. Роль сразу появляется во всех открытых панелях (группа «Мои роли»
в выпадающем списке) и сохраняется в `custom_roles.json` рядом со скриптом, так что
переживает перезапуск сервера. Кнопка **✕** удаляет свою роль; встроенные защищены.

## Память: агент как сущность с состоянием

Самая наглядная проверка того, что агент — объект, а не вызов. Один и тот же вопрос
одному и тому же агенту:

| | Ответ | Токенов в запросе |
|---|---|---:|
| «Запомни: меня зовут Алекс» → «Как меня зовут?» с памятью | **Алекс** | 60 |
| тот же вопрос после снятия галочки «память» | **Майкл** | 35 |

Без памяти агент не просто «не знает» — он выдумывает имя, потому что в запрос ушёл
только system-промпт и текущий вопрос. Разница в `prompt_tokens` (60 против 35) — это
и есть вес истории диалога.

## TOON вместо JSON для данных в промпте

[TOON](https://github.com/toon-format/toon) — компактная запись тех же данных: ключи
объявляются один раз в заголовке, дальше идут только значения. Реализован свой кодер
на стандартной библиотеке (`toon.py`), покрывающий случаи, где формат выигрывает:
таблицы однородных записей, инлайн-массивы примитивов, вложенные объекты.

Те же данные в двух форматах:

```json
{"sales": [
  {"day": "пн", "cups": 142, "revenue": 32660, "weather": "дождь"},
  {"day": "вт", "cups": 158, "revenue": 36340, "weather": "облачно"}
]}
```

```
sales[2]{day,cups,revenue,weather}:
  пн,142,32660,дождь
  вт,158,36340,облачно
```

На встроенном примере (неделя продаж, 7 записей) TOON занимает 238 символов против
815 у JSON с отступами и 483 у компактного — короче на 71% и 51%.

### Замер на живых запросах

Один и тот же набор данных и вопрос «в какой день продали больше всего чашек»
(верный ответ — пт, 187), по три прогона при `temperature=0`:

| Модель | JSON, токенов | TOON, токенов | Экономия | Верных ответов JSON | Верных ответов TOON |
|---|---:|---:|---:|---:|---:|
| `deepseek-chat` | 364 | 198 | −46% | 3 из 3 | **0 из 3** |
| `qwen/qwen3.8-27b` | 466 | 242 | −48% | 3 из 3 | 3 из 3 |
| `openai/gpt-oss-120b` | 424 | 257 | −39% | 3 из 3 | 3 из 3 |

**Экономия подтвердилась везде — 39–48% токенов запроса.** А вот понимание формата
оказалось не бесплатным: DeepSeek на TOON стабильно ошибался, отвечая «чт, 169» вместо
«пт, 187», хотя тот же вопрос по тому же JSON решал верно все три раза. Две модели Groq
прочитали TOON без единой ошибки.

Вывод практический: TOON экономит заметную долю бюджета на табличных данных, но это
компромисс, а не бесплатный выигрыш — **перед внедрением надо проверять на своей модели**,
что она читает формат правильно. И проверять именно ответами, а не «на глаз»: экономия
видна сразу, а деградация понимания — только на контрольных вопросах.

Отдельно стоит помнить, где формат не помогает вовсе: на прозе, на глубоко вложенных
и разнородных структурах, а на чисто плоской таблице обычный CSV будет ещё короче.

## Технические заметки

- Тело запроса к API — фиксированный OpenAI-совместимый JSON, его формат диктует
  провайдер. TOON применяется **внутри промпта**, к данным, а не к транспорту.
- Данные подставляются в вопрос заново при каждом запросе и намеренно **не попадают
  в историю диалога** — иначе они копились бы в памяти с каждой репликой.
- Groq и DeepSeek различаются форматом ответа (у Groq есть скрытые reasoning-токены
  в отдельном поле). Разница спрятана в `providers.call()`, агент её не видит.
- Разбор входящего запроса на сервере целиком под `try`: битый payload возвращает JSON
  с текстом ошибки, а не рвёт соединение.
