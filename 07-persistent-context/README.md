# 07 — Сохранение контекста

**Задание:** добавить агенту сохранение контекста — хранить историю диалога в JSON или
SQLite, при перезапуске загружать её обратно и продолжать диалог так, будто агент не
выключался. Проверить на практике: начать диалог, перезапустить приложение, продолжить
и убедиться, что агент помнит прошлые сообщения.

## Запуск

```bash
cd 07-persistent-context
python3 web.py                  # откроется http://localhost:8007
python3 check_restart.py        # автоматическая проверка «диалог → перезапуск → диалог»
```

## Чем отличается от дня 6

В дне 6 агент жил только в памяти процесса: история в `self.history`, реестр агентов в
словаре — после `Ctrl+C` всё пропадало. Здесь то же самое, но состояние пишется
в **SQLite** и поднимается обратно при старте.

```
день 6:  браузер → web.py → Agent(в памяти) → LLM
день 7:  браузер → web.py → Agent ⇄ storage.py → agents.db
                              └──────────────→ LLM
```

Восстанавливается всё рабочее место, а не только переписка: панели, их настройки,
история и накопленные счётчики. Открыл страницу после перезапуска — продолжаешь с того
же места.

## Схема базы

```sql
CREATE TABLE agents (
    id TEXT PRIMARY KEY,        -- a1, a2, …
    settings   TEXT NOT NULL,   -- JSON: модель, роль, температура, память, данные
    stats      TEXT NOT NULL,   -- JSON: вызовы, токены, стоимость
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE TABLE messages (
    id       INTEGER PRIMARY KEY AUTOINCREMENT,
    agent_id TEXT NOT NULL REFERENCES agents(id) ON DELETE CASCADE,
    role     TEXT NOT NULL,     -- user | assistant
    content  TEXT NOT NULL,
    created_at TEXT NOT NULL
);
```

Реплики пишутся сразу после успешного ответа модели — падение процесса не теряет
последнюю пару сообщений. Соединение открывается на каждую операцию: панели пишут
параллельно, а одно соединение sqlite3 между потоками делить не разрешает. Включён
режим `WAL`, чтобы чтение не блокировалось записью.

Посмотреть сохранённое можно любым клиентом, не запуская приложение:

```bash
sqlite3 agents.db "SELECT agent_id, role, substr(content,1,40) FROM messages ORDER BY id;"
```

## Проверка на практике

`check_restart.py` проделывает сценарий из задания сам и печатает каждый шаг.
Реальный вывод:

```
1. Первый запуск: начинаем диалог
   создан агент a1
   → Запомни: меня зовут Алекс, я пишу на Python.
   ← Запомнил: Алекс, Python. Чем помочь?
   → Как меня зовут?
   ← Алекс.

2. Выключаем приложение
   процесс сервера остановлен

3. Что осталось на диске
   файл agents.db, 4096 байт
   a1  user      Запомни: меня зовут Алекс, я пишу на Python.
   a1  assistant Запомнил: Алекс, Python. Чем помочь?
   a1  user      Как меня зовут? Одним словом.
   a1  assistant Алекс.

4. Запускаем заново и продолжаем тот же диалог
   поднято агентов: 1, сообщений: 4
   имя агента после перезапуска: Память, вызовов в счётчике: 2
   → Как меня зовут и на чём я пишу?
   ← Алекс, Python.

5. Итог
   агент помнит имя и язык после перезапуска: ДА
```

Ключевой момент — в шаге 4 имя агенту в этой сессии **не называли**. Он мог узнать его
только из базы.

Проверено также: три панели пишут одновременно без ошибок блокировки; «Сбросить диалог»
чистит историю и в базе, оставляя самого агента; «Закрыть панель» удаляет агента вместе
с перепиской, и после перезапуска он не возвращается.

## Подводный камень: нумерация агентов

Счётчик id при старте продолжается с максимума в базе (`storage.max_agent_number()`).
Без этого после перезапуска новый агент получил бы `a1` — то есть id уже
восстановленного — и затёр бы его историю. В проверке это видно: после восстановления
`a1, a2, a3` следующий созданный агент получил `a4`.

## Граница, о которой стоит помнить

Сохранение контекста и размер контекстного окна — **разные вещи**. В базе лежит вся
переписка целиком, но в запрос к модели уходят только последние `memory_depth` сообщений
(настройка «Память» в панели). То есть агент ничего не забывает на диске, но показывает
модели ограниченное окно — иначе длинный диалог рано или поздно упрётся в лимит модели
и в стоимость: каждый запрос оплачивается вместе со всей отправленной историей.

Файл `agents.db` — локальные данные, в репозиторий он не попадает (см. `.gitignore`).
